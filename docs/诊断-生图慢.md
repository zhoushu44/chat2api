# 生图慢 · 线上诊断报告

> 诊断时间：2026-10-02 23:50 (CST)｜目标服务器：195.72.185.32
> 数据来源：Go 版 16 条真实分段计量日志 + 容器运行时状态 + 网络探测

## 一、结论（一句话）

**慢的 93% 来自上游 OpenAI（SSE 流 59% + 轮询等待 13% + requirements/bootstrap 8%），我们本地环节合计只占 2.5%。**
真正需要立刻处理的是另外两个**故障级问题**：sub2api 崩溃循环（5750 次）、号池图片额度耗尽。

### 关键读法

1. **SSE 流 = 上游生成图片本身耗时（17.6s 均值）**，这是 OpenAI 服务端排队 + 出图的时间，客户端无法优化。
2. **轮询等待出现双峰**：多数请求 1.0s（polls=2，命中很快），但少数请求 16~31s（polls 7~10）。
   对应 22.0s 和 41.1s 两条日志——**上游偶发"出了会话但附件还没就绪"**，靠多轮轮询补齐。
3. **bootstrap 13.1s 的异常值**（那条 33.2s 请求）是首次建连开销，OPT-3 缓存生效后其余都是 0。
4. 本地处理（编码/resolve/下载/准备）**合计占比 2.5%**，不是瓶颈。

## 三、两个真正的故障（需立即处理）

### 3.1 sub2api 崩溃循环 —— 重启 5750 次 🔴

```
RestartCount=5750    Started=2026-10-02T15:50:49Z    RestartPolicy=always
日志: Failed to initialize application: acquire migrations lock:
      dial tcp 192.6.121.16:35432: connect: connection timed out
```

- **现象**：每 2 分钟崩溃一次，无限重启（`always` 策略）
- **根因**：sub2api 的 Postgres 数据库走 `192.6.121.16:35432`（= 你的 socks5 代理出口 `192.6.121.16`），该 IP 现已**完全不可达**（`DB_UNREACHABLE`）
- **影响**：`token.86969678.xyz` → nginx → sub2api → 下游，**sub2api 是链路必经环节**。它每 2 分钟有约 2 分钟不可用窗口，命中窗口的请求直接失败或超时重试 → 表现为"生图很慢/偶发失败"

### 3.2 socks5 代理 192.6.121.16 已死 🔴

```
socks5h://192.6.121.16:11032  →  无响应（SOCKS_UNREACHABLE）
```

- 该代理同时承担：sub2api 的 DB 通道 + README 里记录的生图出站代理
- 服务器**直连** chatgpt.com 只需 3.3s TLS 握手（网络本身通畅），说明不是墙的问题，是**代理 IP 本身失效**
- 影响：凡依赖该出口的链路全部超时

### 3.3 号池图片额度耗尽 🟡

```
backend_user_info_result: "type": "free", "quota": 25, "status": "正常"
```

- 账号显示"正常"但 quota 字段是**文本对话额度 25**，图片额度需另看（历史记录里 image quota 耗尽会 429）
- 老 Python 版 `accounts.json` 最后修改 23:20，池子在动；但 30 分钟内 Go 版 0 请求、老版也无成功生图日志 → **实际无可用生图供给**

## 四、部署现状（一个隐患）

| 容器 | 镜像 | 端口 | 状态 | 说明 |
|---|---|---|---|---|
| `chatgpt2api` | ghcr.io/yukkcat/chat2api:v2.7.0 | 3000→80 | Up 8 天 | **老 Python 版，实际在服务** |
| `chatgpt2api-13` | zhoushu1/chat2api:15.0 | 3077→3077 | Up 2h | Go 新版本，**近 6h 零生图请求** |
| `sub2api` | — | 8080 | 崩溃循环 | nginx `token.` 域名的上游 |

**隐患**：nginx 的 `token.86969678.xyz` 指向 **sub2api:8080**（不是 chat2api），而 sub2api 正在崩溃循环 → 对外主入口实际是坏的。Go 版虽然健康（healthz 200，7ms），但没接到流量。

## 五、建议动作（按优先级）

### P0 · 立即（恢复可用性）

1. **停掉 sub2api 的崩溃循环**，阻止资源浪费：
   ```bash
   docker update --restart=no sub2api && docker stop sub2api
   ```
   或修好它的数据库通道（把 `192.6.121.16:35432` 换成可达的 DB 地址）

2. **换掉失效的 socks5 出口** `192.6.121.16`：
   - 服务器上另有 `warp`、`mihomo`、`proxypilot` 等代理容器，可切换到可用出口
   - 换好后同步更新 sub2api 的 DB 配置 + chat2api 的 `CHATGPT2API_PROXY`

3. **确认对外入口指向**：如果要走 Go 版，把 nginx `token.` 的 `proxy_pass` 从 `:8080`(sub2api) 改到 `:3077`(chat2api-13)，
   或修复 sub2api 让它恢复转发

### P1 · 短期（把慢降下来）

4. **补号 / 等待额度恢复**：账号 `restore_at` 显示 2026-10-03 15:00~15:19 恢复，可先观察；同时提高注册补号频率
5. **轮询策略微调**：把 `pollwait` 中位数 1s 但长尾 16~31s 的情况纳入观察——
   当前 `polls=2` 命中率不错，长尾是上游附件就绪延迟，**建议不动**（改小反而增加空轮询）

### P2 · 不建议做

- ❌ **不要为了"快"去砍 SSE 流或轮询**：SSE 17.6s 是上游出图必需时间，砍掉只会拿到空结果
- ❌ **不要盲目调大并发**：瓶颈在上游账号额度，不在本地并发；账号不够时并发只会全失败
- ❌ **不要动 12 段计量日志**：它现在是唯一能定位瓶颈的工具

## 六、与超分功能的关系

超分**不是**慢的原因：
- 超分只对 `size=2k/4k` 生效，且新增耗时仅 **3~6s**（实测）
- 这 16 条日志全部是 `size` 未触发超分的普通请求（Go 版超分功能尚未部署，且 `SUPERRES_ENABLED` 未设）
- 当前慢的构成与超分无关，**先修 P0 故障再谈超分上线**
