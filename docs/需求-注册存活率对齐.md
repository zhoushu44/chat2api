## 需求 1（P0）：注册即收口 —— 强制密码 + TOTP 2FA + 注册后立即验活

### 1.1 目标

注册成功的账号必须同时满足：**有密码、已绑 TOTP 2FA、access_token 当场验活通过**。任一不满足则视为注册失败，不写入产出、不导入号池。

理由（对齐 abai-freegpt）：
- 无密码账号只能靠临时邮箱收码登录，**邮箱域名失效即永久丢失**；
- 绑了 TOTP 才能在 access_token 被 revoke 后用「邮箱 + 密码 + TOTP」走协议登录恢复，**不依赖邮箱 OTP**；
- 注册后立即验活可挡掉「刚签发就失效」的脏号，避免污染号池、拉低存活率统计。

### 1.3 需求条目（逐项验收）

#### 1.3.1 强制设密码

- [x] HTTP 模式忽略配置里的 `http_set_password=false`，**始终设密码**；注册链若未拿到 `password`（`_register_password` 未成功）→ 判定注册失败（`fail_http_no_password`），不产出、不导入。
- [x] 产出 `extra.has_password` 必须为 `true`；为 `false` 的记录不得进入 `api_keys.txt` / `accounts.jsonl`。
- [x] schema 里 `http_set_password` 改为只读展示（或直接移除该开关），help 说明「强制开启，无密码账号会随邮箱域名失效永久丢失」。

#### 1.3.2 强制绑定 TOTP 2FA

- [x] HTTP 模式忽略 `http_bind_2fa=false` / `enable_2fa=false`，**始终绑定 TOTP**。
- [x] `_bind_totp_2fa` 失败（含 `mfa_info` 异常、`enroll` 非 200、`activate_enrollment` 非 200、缺 `secret`/`session_id`）→ 判定注册失败（`fail_http_no_2fa`），不产出、不导入。**这改变了当前「失败返回 {}、绝不影响注册结果」的语义。**
- [x] 幂等分支保留：`mfa_info.mfa_enabled=true` 时视为已绑，但此时拿不到 `totp_secret` → 视为失败（无法保证后续可恢复），或者单独标记 `2fa_preexisting` 并按失败处理（二选一，实现时在 PR 说明中确认）。
- [x] 产出 `extra.totp_secret` 非空、`extra.mfa_enabled=true`。

#### 1.3.3 注册后立即验活

- [x] HTTP 注册拿到 `access_token` 后，**同一会话内**（复用相同 session / 代理 / 指纹，不新建连接）调 `GET https://chatgpt.com/backend-api/me`，2xx 视为有效。
- [x] 验活失败（401 / 403 / 非 2xx / 网络异常）→ 判定注册失败（`fail_http_not_alive`），不产出、不导入。
- [x] 验活放在**绑定 2FA 之前**还是**之后**需在实现时确认：建议先验活（拿 token 立即用），再绑 2FA；两者都通过才 `ok_result`。→ **实际采用：先绑 2FA 再验活（用户决策 3B）**，保证最终态即交付态。
- [x] 日志明确输出：`[验活] /backend-api/me 200 OK` 或 `[验活] 失败 [401]`。

#### 1.3.4 产出与导入收口

- [x] 上述三项任一不满足 → `AccountResult.status` 为失败态，`dbg.fail(...)`，**不写 `api_keys.txt`、不写 `accounts.jsonl`、不触发 auto import**。
- [x] 成功日志追加：`✅ 注册收口完成：密码 + TOTP 2FA + 验活 全通过`。
- [x] `extra` 至少包含：`has_password=true`、`mfa_enabled=true`、`totp_secret=<非空>`、`alive_verified=true`。

### 1.4 不改动范围（明确边界）

- 不引入 abai 的 SMS 接码 / refresh_token 强取流程（当前 Codex OAuth 普遍被 `/add-phone` 拦截，属已知限制）。
- 不改动 browser 模式既有步骤链（step01~step06），本需求只覆盖 `register_mode=http`；browser 模式的强制化列入后续需求。
- 不改动 Go 侧 `/backend-api/me` 探针实现（`internal/backend/verify.go` 已存在，本次只在 Python 注册链内做等价请求）。
- 不动邮箱 / 代理 / 打码 Provider 实现。

### 1.5.1 「强制 2FA 是否拉低成功率」专项结论（2026-09-13 实测）

**结论：2FA 环节本身 0 失败，未拉低成功率。** 5 个账号中 4 个成功，全部 5 个账号都成功执行了 `[2FA] 绑定 TOTP`：

| 账号 | 2FA 绑定 | 验活 | 最终 |
|---|---|---|---|
| 1/5 | ✅ 成功 | ✅ 200 | ok |
| 3/5 | ✅ 成功 | ✅ 200 | ok |
| 5/5 | ✅ 成功 | ✅ 200 | ok |
| 4/5 | ✅ 成功 | ✅ 200 | ok |
| **2/5** | ❌ **未走到**（流程更早失败） | — | fail |

**唯一失败（2/5）根因不是 2FA，而是 MailNest 邮箱层错误**：

```
[5/9] 邮箱验证码...  →  密码注册成功  →  OTP 已主动重发
收码失败: MailNest 业务错误 D0004: 当前无法对此邮箱执行该操作
邮箱验证码获取失败（超时或未收到）  ← 在 [2FA] 之前就失败了
```

该账号在收 OTP 阶段就失败（`D0004` 是 MailNest 侧「该邮箱不可操作」，属邮箱池/域名侧问题），**根本没有走到 2FA 环节**，因此不计入 2FA 失败。

**与改造前基线对照**：`data/register.json` 中 09:43 那次任务（无 2FA）同样 1/1 成功、同样卡在 add-phone 拿不到 refresh_token；本次 80% 失败点与之相同（都是邮箱/网络层），**说明强制 2FA 没有引入新的失败面**。

**风险提示（保留）**：本轮 2FA 零失败，但样本仅 5 个。若后续大批量出现 `fail_http_no_2fa` 占比 >10%，再评估给 `mfa/enroll` 加一次重试。

## 需求 4（P2）：per-node 封禁检测 + 自愈 + per-worker 端口隔离

### 4.1 背景
abai 用 Mihomo 的 `REGISTER-SLOT-01..50` 给每个并发 worker 独占一个出口 listener，节点被封只换该 slot；并有「节点连续 N 次收不到验证码 → 判 IP 被封 → 暂停 + 后台探测恢复」的自愈机制。当前 chat2api 只有 wary 粘性 sid + 失败冷却，**无 per-node 封禁判定**。

### 4.2 需求条目
- [ ] 节点级计数：同一出口连续 N 次（默认 3）收不到验证码 → 标记该节点 `blocked`，暂停使用。
- [ ] 后台探测线程：每 600s 轮转探测一批被封节点，恢复即解除。
- [ ] （可选）per-worker 端口隔离：评估是否引入 Mihomo slot 方案，或先用现有 wary 池做节点级隔离。
- [ ] 复用已有 `internal/proxy/proxy.go` 的冷却/成功率计数，不新造轮子。

### 4.3 测试
- [ ] T4.1 人为注入一个「收不到码」的坏节点，确认连续 3 次后被封停。
- [ ] T4.2 确认被封节点不再被分配。
- [ ] T4.3 探测线程能把恢复的节点解封。
- [ ] T4.4 批量并发下无节点被重复踩踏。
